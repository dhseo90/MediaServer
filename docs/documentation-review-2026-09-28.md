## 1. 결론

README의 문장만 줄여서는 충분하지 않다. 현행 제품 안내에 내부 단계·승인·검증 이력이 들어가 있고,
녹화 구조가 변경된 뒤 설정·구조·검증 안내의 일부 설명은 이전 계약에 남아 있다.
녹화 설명의 정확도를 맞추고, 공개 진입 문서에서 내부 기록을 분리해야 한다.
실행 순서는 후속 사용자 지시에 따라 5절의 조사 → 정책 → 검증기·생성 도구 → 실제 문서 정리로 보완한다.

확정한 핵심 문제는 다음과 같다.

1. 설정 문서의 삭제 순서·저장소 구성·이벤트 영상 형식이 현행 관리 녹화 경로와 맞지 않는다.
2. README는 내부 단계와 release 절차 설명이 많지만, 실제 녹화의 사용 흐름을 충분히 설명하지 않는다.
3. 검증기가 공개 README에 내부 단계의 고정 문구를 요구한다. 본문 정리와 검사 기준 정합을 함께 다뤄야 한다.
4. 현재 정책·사용법과 과거 버전의 현재형 설명이 섞여 있다.
5. 중앙 기록과 공개 문서에 상세 이력이 누적되어 목적별 탐색이 어렵다.

이전의 “릴리즈 문서 정비가 충분하다”는 판단은 정정해야 한다.
문서 링크·metadata 검사 통과가 사용법의 정확성이나 가독성까지 보장하지는 않는다.
이 리뷰는 기존 제품 검증·PR·태그·Release 결과를 실패로 바꾸거나 취소한 것이 아니다.

1. A 현재 사용법, B 현재 기술 계약, C 현재/미래 계획·미완료, D 테스트 정의·fixture/golden, E 종료 실행 기록, F 재생성 임시/중복, G 라이선스·출처, H 추가 확인으로 나눈다. 여러 성격이 섞인 파일은 필요한 내용을 분리한 뒤 정리한다.
2. 파일명·버전 접두사·크기만으로 삭제하지 않는다. 대형 과거 로그의 개별 결과를 전부 재판정하지 않되 현행 계약 혼입·현재 소비자·원본 보존을 확인한다. 7절의 기존 잠정 분류는 삭제 허용 목록이 아니다.
3. 수정·축약·삭제 전 현재 바이트와 유지되는 이력의 Git blob을 대조한다. 이미 동일한 원본이 있으면 기존 commit/path를 사용한다. 보존되지 않은 비민감 자료만 필요한 별도 보존 커밋을 만든다.
4. LFS pointer·외부 URL·만료될 CI artifact는 원본 바이트 보존으로 세지 않는다. 비밀·운영 자료는 새로 커밋하지 않으며 정제본과 원본을 동일한 증거로 표시하지 않는다. 로컬/원격 보존 여부는 별도다.
5. 정책 변경, 도구 변경, 문서 정리의 논리 단위로 커밋한다. 필요한 보존 커밋과 삭제 커밋은 반드시 분리하고 squash로 보존을 없애지 않는다. 실패 사실 보존과 실패한 제품의 합격 판정도 분리한다.
6. 기존 공개 태그는 움직이지 않는다. 문서/증거 수명 유지보수와 제품/배포 정확성 수정을 구분한다. 이번 네 단계의 push/PR/merge/tag/release는 승인 범위가 아니며 자동 수행하지 않는다.
7. 보호 목록에는 현행 계약·v4.2 이후 계획·미해결 이슈·현재 테스트 정의·회귀 fixture·golden/baseline·sample/provenance·라이선스와 사용자 변경을 포함한다. 경로 이탈·symlink 외부 대상·실행 중 자료·소유 불명 자료는 삭제하지 않는다.
8. 이 보고서도 정리 종료 때까지 유지한다. 필요한 보존 여부를 같은 기준으로 확인한 뒤 마지막 정리 대상에 포함한다. 완료 사실은 정리 커밋 본문과 간결한 최종 보고에 남기며 새 대형 감사/인계 문서로 대체하지 않는다.

색인에는 버전·확인된 tag/source·실제 보존 commit·원래 경로·필요한 종료/로컬/원격 구분만 남긴다.

한국어/영어의 녹화·재생 설명을 대조하고 공개 문서의 기본 언어는 한글로 유지한다.
대표 이미지·회귀 baseline은 보호하며 상하좌우 잘림이나 과도하게 긴 축소 이미지를 만들지 않는다.
기존 이미지의 육안 검토와 링크 검사는 실제 UI 풀테스트 PASS가 아니다. 새 촬영이 필요하면 범위·실행/정리 조건을 별도로 판단한다.

### 5.5 모델·검증·최종 판정 경계

- 이번 문서 작업의 사용자 지정 Astra/xhigh를 우선한다. 메인 외 담당자는 필요할 때만 최대 한 명이며 하위 재위임은 금지한다. 이번 통합 계획에 새 서브에이전트는 사용하지 않는다.
- `openai-docs` 확인 절차에 따라 공식 모델 등재, 설치 Codex 지원, 계정 가용성, 프로젝트 설정과 현재 세션 적용을 구분한다. 공식 자료를 열었다는 것만으로 설치·계정·effective 설정 확인 완료라 하지 않는다. 관련 설정의 실제 수정·전수 확인은 2/4다.
- 모델/설정 참고는 [공식 모델 목록](https://developers.openai.com/api/docs/models), [Codex 설정](https://learn.chatgpt.com/docs/config-file/config-reference), [AGENTS 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 등 사용자 지정 공식 자료를 사용한다. 역사 기록의 실행 모델·시각·PASS/FAIL provenance는 최신 값으로 바꾸지 않는다.
- 검증기 반례는 임시 fixture 저장소에서 수행한다. 정상 링크뿐 아니라 잘못된 앵커/누락, 보존 commit 부재/내용 불일치, 보호 대상/경로 이탈/실행 중 자료, 실제 FAIL·다음 단계 실패 전파와 정확한 대상만 삭제하는 경우를 확인한다.
- 일반 build/test가 과거 로그 fetch/복원을 요구하게 만들지 않는다. source archive/shallow에서도 원래 가능한 검증은 유지하며 Git 전용 보존 감사는 적용 불가와 PASS를 구분한다.
- 최종 짧은 검증은 관련 Markdown 링크·앵커·이미지·목적별 도달성, 남은 scripts/config/workflow/test 소비자, 정책/설정 정합, 변경 도구 자체검증, diff와 기록 재조회다. 과거 제품 PASS를 복사하거나 이번 도구 검사를 제품 전체 PASS로 보고하지 않는다.
- 실제 UI 풀테스트·30분·120분·외부 서비스/실기기·제품 기능 검증은 이번 정리 실행 범위가 아니다. 기존 릴리즈의 필수 검증 기준 자체를 완화한다는 뜻도 아니다.
- 최종 보고는 유지/통합/이동/삭제/보류, 문서 수·현재 트리 관련 바이트 변화, 정책·모델 확인 결과, 보존/정리 commit, 실제 조회 명령, 실행/미실행, working tree·사용자 변경, 로컬/원격 보존을 구분한다. 현재 트리 감소를 `.git` 이력 용량 감소라고 주장하지 않는다.

**현재 상태: 4개 지시의 통합 계획만 반영. 1/4 조사 완료 아님. 실제 다음 착수는 1/4이며, 2/4~4/4나 v4.2.0 개발을 자동 실행하지 않는다.**
