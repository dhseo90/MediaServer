# 잔여 지연 판정 — 실제 HTTP 관측 및 선행 작업 실패

독자: 녹화 구현·검증 담당자. lifecycle: v4.1.0 진단 이력. 정책은 AGENTS.md, 중앙 결과 source-of-truth는 release-test-records.md이며 이 파일은 상세 증거다.

## 결론

전체 지연 판정 미완료. LP01 명령은 exit1/51.703초로 종료했다. 관측한 timeline494개는 모두HTTP200, p50 33ms/p95 50ms/p99 115ms/최대585ms, 기존4초 초과0이다. 단, 같은 이벤트의 job이 not-created→intent→failed, 출력0으로 끝나 latency-transition-timeout이 발생했다. 지연 묶음PASS 또는 실제 제품 성능 합격이 아니다. 작업이 성공한 뒤5초 조회는 미실행이다.

제품 수정·커밋·푸시는 하지 않았다. LP02 16/32원본 누적 검사는 선수 실패로 미실행이며 테스트 전용3파일 초안만 작성했다. 직전8원본의1.227초는 기존 별도 계측값이지 이번HTTP585ms와 직접 비교 가능한 동일부하값이 아니다.

## 실행/해석 경계

- 명령: `node scripts/internal/verify_recording_current_app.mjs --latency-only`
- 기준: HEAD `679273d8a50c1a49e5e1693079a345f02725be97`, 직전 최종 제품build 사용. 이번 제품파일 수정 없음.
- 동일 이벤트 참조를 가진 durable EventRecord 발생은 확인했으나 job실패 상세 failure_reason은 기존요약이 출력하지 않았다. 서버stdout/stderr는 기존runner가 용량만 집계하며 본문을 보존하지 않는다. 삭제된자료를 추정복원하지 않는다.
- 시간초과는 개별HTTP4초가 아니라 정상 job출력 전이를 기다리는30초 조건이다. HTTP header 최대584ms이며 body는반올림0ms다. 새proof/최대잠금/환경 중 어느 것이 job실패 원인인지 확정하지 않는다.
- P0-HTTP02 완전성 판정은 이번에 바꾸지 않았다. 실패 작업을부분성공으로 간주하거나timeout을늘리지 않았다.
- 다음 조건: 실패코드를 typed Catalog 또는 안전한 로컬 진단에서 allowlist로 보존하는 최소계측을 확정하고 같은실제앱1회로 원인확인. 제품수정이필요하면 범위확정후 처리. 그뒤 LP01과 LP02를 재개한다. 공개API/schema/운영계정 변경불필요.
