# v4.3.0 자원 수명·Visual Vector Search 개발 계약

## 범위와 상태

2026-10-04 사용자가 승인한 작업은 보고한 이슈 1~10의 개발, 단기 직접 검증,
분할 커밋과 마지막 브랜치 push다. 기준은 최신 main `8244db05`에서 분기한 `v4.3.0`이다.
릴리즈용 안정화 묶음·30분·120분·UI 풀테스트·predev, PR·병합·tag·Release·브랜치 삭제는
이번 실행 범위 밖이다. 10번은 개발 품질·영향 회귀 및 릴리즈 검증 준비까지 수행한다.
이 문서는 설계와 남은 결정의 기준이며 실행 PASS 기록이 아니다.

1~4 자원 선행 과제를 통과한 뒤 5~8 벡터 검색을 제품에 연결하고 9 상시녹화 색인을 확장한다.
모델 출처 조사와 값 계약 설계는 선행 과제 동안 가능하지만 제품 색인 부하를 먼저 추가하지 않는다.
기능별 독립 기대값은 [테스트 정의](../../project-feature-test-inventory.md#v430-자원-수명과-벡터-검색)에 둔다.

## 1. 지원 범위와 개발 판정 기준

확인한 개발 호스트는 macOS arm64, 논리 CPU 10개, RAM 24GiB다. 사용자는 별도 지정 운영값이
없다고 답했다. 아래는 후속 실행 전에 정한 개발 목표이며 검증된 지원 보장이 아니다.
기존 2채널·120분의 관측값을 상한이나 합격선으로 전환하지 않는다.

| 축 | 개발 목표·예산 |
| --- | --- |
| 녹화·검색 규모 | 최대 8채널, 누적 mutation identity 100,000개, 활성 검색 문서 최대 100,000행. 바이트 제한이 먼저 적용될 수 있음 |
| 논리 보유량 | Catalog/Journal의 이력·현재 상태를 구분해 계상. 해당 규모의 합계 512MiB 이하 목표. 기존 검색 projection 64MiB, snapshot 합계 128MiB/8개/5분 유지 |
| 동시 부하 | 검색 요청 4개와 녹화 병행. 공유 미디어 callback에서 검색·임베딩 실행 금지 |
| 검색 지연 | warmup 후 동일 조건 반복에서 구조화 검색 p95≤2초/최대5초 목표. 대기·준비·조회 비용 분리. 미준비/오류를 지연 성공 표본으로 세지 않음 |
| 녹화 진행 | 입력 packet 진행과 파일 확정이 계속되고 기존 독립 파일·시간·순서 기대값 충족. 처리 불가를 정상 녹화로 보고하지 않음 |
| 프로세스 메모리 | 개발 혼합 부하 peak RSS 4GiB 이하 목표. logical bytes·현재 RSS·peak RSS는 별도 값으로 기록 |
| 작업 공간 | 격리 fixture와 빌드/모델 준비 공간 8GiB 이내. 실제 미디어 quota·제품 메타데이터·색인·복제·로그를 따로 계상 |
| 벡터 부하 | 실제 모델 선택 후 추론 workspace·동시 작업·색인 byte 및 지연/품질 기준을 첫 실행 전에 확정. 임의 벡터 fixture를 실제 모델 품질로 간주하지 않음 |

입력 규모는 지원 기간의 환산값이 아니다. 누적 이력은 계속 증가하므로 목표 밖의 장기 운용을
보장하지 않는다. 초과 시 필수 이력 삭제나 조용한 검색 truncation으로 예산을 맞추지 않는다.
지원·오류 정책이 저장 계약 변경을 필요로 하면 별도 설계 판단을 먼저 한다.

## 2. 자원 원인과 변경 경계

- 활성 미디어를 고정하고 이력만 늘린 조건, 검색 문서만 늘린 조건, 동시 요청 조건을 분리한다.
- Journal의 검증된 identity chain과 조회용 색인, Catalog의 최소 ID/retired receipt,
  원본 모델·요청 중 사본·snapshot 및 allocator 잔류를 구분한다.
- 첫 조사에서 Journal의 historical identity 조회 색인은 chain에 이미 있는 entity/time/digest를
  합친 문자열을 다시 보유한다. 같은 identity 문자열을 필요할 때 같은 함수로 복원하는 방안은
  저장 형식·최소 증거 삭제 없이 중복 상주량을 줄일 수 있다. 실제 절감과 충돌/복구 회귀를 먼저 확인한다.
- 검색 mutex 아래 준비 직렬화, 전체 문서 복사와 만료 후 idle snapshot 보유를 직접 대조한다.
  비용 개선이 기존 불변 페이지 멤버십·현재 권한·삭제 판정을 바꾸지 않게 한다.
- RSS 전부를 누수로 가정하지 않으며 제한된 논리 절감 하나로 전체 선행 과제를 완료하지 않는다.

### 선행 개발 profile의 검증 경계

100,000개 기존 예약 이력이 있는 B root에 8채널/10,000관측/4검색을 추가한 단기 profile을
검증했다. 입력은 160×90 H.264, 파일 시각30fps/90packet, packet 공급 간격4ms이며 채널별
세 개 파일을 확정했다. 이 조건과 별도 삭제 이력·회전/복구·idle 수명 회귀로 선행 개발 기준을
판정한다. 실행 수치·최초 실패/수정/재검증은 [개발 기록](../../release-artifacts/v4.3.0/development/README.md)에
한 번만 보존한다. 임의 해상도/FPS·장시간·임베딩 혼합 부하의 완료를 뜻하지 않는다.

## 3. 임베딩·색인 계약

image/text/cross-modal 계약은 model revision/weight digest, tokenizer, 전처리, 차원,
정규화와 유사도 정의를 묶은 contract ID로 구분한다. 같은 차원의 다른 모델도 같은 공간으로
합치지 않는다. 계약 변경은 별도 공간 재색인이며 과거 벡터의 ID만 바꾸지 않는다.

실제 로컬 모델은 Google SigLIP2 base patch16-224를 채택한다. 사용자가 약 1.5GB 고정 가중치와
토크나이저 다운로드, 격리 Python 변환 도구 및 C++ SentencePiece 의존 준비를 명시 승인했다.
모델 선택은 설치·실행·품질 검증 완료가 아니다. 전역 환경을 변경하지 않고 Git 밖의
`models/v430-siglip2/`, `third_party/v430-embedding/` 아래에서 준비한다.
공식 revision·파일 hash·Apache-2.0 및 전처리 근거는 채택 시 출처 문서에 고정한다.
원격 provider 호출, 얼굴/신원 검색, 모델 자동 다운로드를 제품 요청 경로에 추가하지 않는다.

이벤트 snapshot과 대표 frame에서 시작한다. 각 색인 문서는 기존 녹화/관측/원본 frame 참조와
contract ID에 결박하며 현재 권한·파일 건강도·삭제 상태를 검색과 재생 시 다시 확인한다.
색인은 재생성 가능한 파생 자료이고 원본의 저장·보존·복구 권위가 아니다.
재색인 중 부분 결과를 완료한 전체 색인으로 게시하지 않는다.

exact top-k를 독립 기준으로 두고 score 동점은 안정 ID로 결정한다. threshold 경계,
NaN/Inf·0 norm·차원/contract 불일치와 빈 결과를 따로 검사한다. 텍스트 유사도는
사건 발생이나 동일 인물의 증거 판단이 아니다. 기존 구조화 결과의 의미를 바꾸지 않는다.

API·UI는 기존 Ops 권한 경계에서 추가하며 Client/viewer 노출과 primary nav 변경을 하지 않는다.
상세 route/control은 구현 전에 테스트 정의에 확정한다. 상시녹화 색인은 후반에 설정 주기와
bounded 작업 수명으로 확장하고 기존 source worker·미디어 blocking 정책을 유지한다.

## 4. 순서와 완료 증거

| 이슈 | 산출물과 다음 단계 조건 |
| --- | --- |
| 1 | 지원 규모·논리/RSS/디스크/진행/지연의 판정 기준 |
| 2 | 같은 조건의 기준 측정과 직접 소유 비용; 미관측을 추정하지 않음 |

| 5 | 실제 선택 모델·tokenizer·contract ID·출처/라이선스·품질 fixture 고정 |
| 6 | 이벤트/대표 frame 색인·삭제·재구축·중단 복구·이전 contract 분리 |
| 7 | exact top-k 독립 순위·threshold·안정 정렬 반례 |
| 8 | 실제 텍스트→영상·권한·결과→현재 재생 연결과 변경 영역 단기 UI |
| 9 | 설정 주기 상시녹화 색인, 자원 admission·종료·재활성화 |
| 10 | 개발 build/영향 회귀·문서·버전 정합·cleanup, 분할 commit와 push; 릴리즈 검증 잔여 보고 |

Evidence Package, VLM 판단, Entity 확정, 자연어 QueryPlan API, 대화형 UI는 후속 버전 범위다.
최종 완료는 부분적인 비용 개선이나 임의 벡터 단위검사만으로 선언하지 않는다.
