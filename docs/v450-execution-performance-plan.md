## 실행 경계와 자원 정책

### 서로 다른 실행 경로

녹화 입력·Writer Finalize, 실시간 VA 분석, 배경 Visual 색인, 사용자 Structured Search,
사용자 Visual Search, 결과·이벤트·Snapshot 게시를 같은 큐나 같은 처리량 지표로 취급하지 않는다.
현재 코드가 이미 분리한 worker·큐·게시 경계를 재사용한다. 서버 전체가 단일 스레드라고 가정하거나
같은 역할의 큐를 중복 구현하지 않는다.

개념적 경계는 **Source/Media 준비 → Decode·전처리 → 추론 → 결과 처리·게시**다.
단계마다 OS 스레드를 하나씩 추가한다는 뜻이 아니다. 먼저 입출력·소유권·동기화·예약량·취소·오류
전파를 정한다. 공유 상태 보호가 필요 없는 느린 작업을 큰 Mutex로 묶지 않고 독립 작업을 겹치되,
초기 비교에서는 기존 추론 동시성을 고정한다. 단계 분리와 추론 동시성 증가의 효과를 섞지 않는다.

추론 결과는 채널·Epoch·PTS·Generation·요청 ID에 결속한다. 순서 의존적인 추적·이벤트·결과 게시는
필요한 순서 복원 또는 직렬화를 남긴다. Source 인증·현재성·삭제·권한·Reader/Hold/Pin 검사는
파이프라인 분리를 이유로 생략하지 않는다. 늦거나 세대가 바뀐 결과를 현재 결과로 게시하지 않는다.

### 제한된 실행과 역압력

새 큐가 실제로 필요한 경우에만 기존 admission과 연결한다. 구현 전에 작업 개수와 총 보유 byte
상한, 대기/체류시간, 포화 시 대기·거부·취소·재개 정책을 함께 정한다. Source·Media Hold·RGB·Tensor의
소유자와 반환 지점, Stop 시 진행/대기 작업의 처리, 예외·부분 실패 반환도 같은 계약에 둔다.
숫자는 기존 예약·실측·작업 범위에서 도출하며 이 문서에서 새 Capacity를 부여하지 않는다.

녹화·실시간 VA·배경 색인의 드롭 정책은 서로 다르다. 미처리 자료를 조용히 버리거나 누락된 색인
coverage를 성공으로 숨기지 않는다. 기존 지원·정확성 정책 변경이 필요하면 별도 결정으로 중단한다.
사용자 검색 응답과 녹화 진행을 보호하면서 배경 색인이 무기한 굶지 않도록 대기·진행을 확인한다.

채택은 검색 완료시간·오류율, Writer 진행·확정 지연·누락, 배경 미처리량·가장 오래된 작업·색인
최신성 지연, 지속 처리량, CPU·메모리·Scratch·FD와 정상 종료를 함께 본다. CPU 100% 자체는
완료 조건이 아니며 OS 스레드 우선순위 변경만으로 해결된다고 가정하지 않는다.

### 워커와 추론 내부 병렬도

외부 분석 워커 수와 ONNX intra/inter-op 설정은 별개다. 기존 설정과 Session 공유 범위를 먼저
확인한다. `1×4`, `2×2`, `4×1`은 필요한 경우의 비교 후보일 뿐 워커 4개가 확정 목표가 아니다.
남아 있는 Mutex 직렬화, Session 수·메모리, 내부 스레드 풀 중첩, CPU 포화와 실제 완료 처리량을
함께 검증한다. GPU/CoreML·새 실행 제공자·추가 모델 복제는 자동 범위가 아니다.

| Preparation Cold Build 병렬화 | 동일 키 중복 Build/Decode와 Owner 증가, 완료 지연 악화로 미채택·복구. 다른 키 개선만으로 State45 해결책으로 재채택하지 않음 |
| Writer Append Delta / Playback Early Reject | 불완전한 변경 증거나 필수 원본 인증 생략을 전제로 구현하지 않음. 기존 계약으로 안전성을 입증할 새 직접 근거와 별도 범위 결정 전 보류 |
| Parser·Projection 추가 미세 최적화 | 완료된 Strict JSON·Capture Reuse 등은 유지. Projection Refresh 개선 근거는 보존하되 혼합 검증 차단으로 미채택. 추가 미세 후보 탐색은 진행하지 않음 |
| R101-C02 v2 | 시간 예산 `BUDGET_UNPROVEN`, 개정·구현 보류. 운영 목적·유한 예산·v1/공식 Gate 인정 관계를 명시적으로 결정하기 전 재개하지 않음 |
| History COW·버전별 저장소 전면 재설계 | v4.5.0 **No-Go**. 새로운 직접 근거와 별도 범위 승인 없이는 재개하지 않음 |

Visual 실험의 원본 판정과 수치는 소급 수정하지 않는다. 서로 다른 요청 집합의 중앙값을 더하고
빼서 순효과를 계산하지 않고, 작은 기준값의 큰 상대 비율만으로 제품 회귀를 확정하지 않는다.
모든 하위 함수가 조금도 느려지지 않아야 한다는 조건은 두지 않는다. 반드시 지킬 정확성·안전·
공식 성능·자원 상한, 실험 전에 정의할 시스템 trade-off, 측정 변동/표본 부족의 미확정을 구분한다.
결과를 본 뒤 후보를 통과시키려고 허용 기준을 바꾸지 않는다.

## 별도 결정: Structured 요청 기준점 B안

최근 검토의 `SOURCE_FRESHNESS_CONTRACT_CHANGE_FEASIBLE`은 **recordings-only 최초 Structured 검색**의
설계 가능성 판단이다. 이 로드맵 편입은 승인됐지만 API/제품 최신성 의미 변경은 **승인 대기**이며
C++ 구현·실행은 이번 승인에 포함되지 않는다. 현행
[구조화 검색 계약](superpowers/specs/2026-10-03-v420-structured-search-design.md#3-read-model과-갱신)을
이미 변경한 것으로 읽지 않는다.

후보 의미는 “최초 Structured 검색은 요청 중 인증한 기준점의 결과를 반환하며, 그 이후 확정된
영상은 다음 새 검색에서 보일 수 있다”이다. 시간 의미는 다음처럼 구분한다.

- **기준점:** Catalog 임계 구역에서 대상 범위의 전체 Raw 행·Lifecycle을 일관되게 확보한 경계.
- **유효성:** 이후 Decode·인증·검증이 모두 성공해야 그 기준점을 사용할 수 있다.
- **검증 완료 시각:** 기준점의 멤버십 시각이 아니며 그때까지 추가된 자료를 모두 포함한다는 뜻도 아니다.

HTTP 도착 시각·Capture 기준점·검증 완료 시각을 동일시하지 않는다. 부분 Capture나 오래된 모델
참조는 기준점으로 인정하지 않는다. 이 구분은 B안 구현 승인이나 현재성 검사 완화가 아니다.

후속 계약 설계에서 다음을 보존해야 한다.

- 기준점 이전 자료의 멤버십·Mapping·`includeUnplaced` 완전성과 현재 Raw 인증,
  손상·Authority 오류 의미 및 오류 우선순위.
- 삭제·Tombstone·Retired·Lifecycle 변경의 기존 거부/fallback, Instance·Scope·Owner·coverage 검증.
- 최종 권한, cursor·재생 시 현재 권한, Reader/Hold/Pin·현재 파일 증명.
- 최대 3회 시도·bounded fallback 및 기존 예약·반환. 추가 장기 Raw·History clone을 만들지 않음.

`new_bound_segment`는 순서 힌트이며 이것만으로 순수 Append나 기존 자료 불변성을 인증하지 않는다.
Structured의 요청 기준점과 Visual의 worker instance + Index Generation은 서로 다른 계약이다.
억지로 동일 Revision에 맞추지 않는다. 불투명 기준점 ID·시각 의미·범위의 응답 표현과 호환성은
후속 설계 대상이며 이번 문서로 공개 필드·schema를 확정하지 않는다.

History COW 없이 가능한 방향이라는 판단과 현재 인증 비용·성능·Resource 안전성이 실증됐다는
주장은 다르다. B안은 Structured 반복 준비/재시도 비용 감소 후보이며 Visual Timeout이나
State45 PASS를 보장하지 않는다. 의미 승인 전에는 현재성 검사를 완화하지 않는다.

## 검증과 완료 조건

검증은 **직접 정확성·동시성·자원 경계**, **개발용 비교·병목 분리**, **공식 통합·장시간·출시 Gate**로
구분한다. 개발 비교 PASS로 공식 PASS를 대체하지 않는다. 공식 실행이 요청 시작 전 준비 단계에서
실패했다면 후보의 요청 처리 성능 회귀로 분류하지 않는다. 제품 결함·측정 결함·환경 차단·미실행을
별도로 남긴다. 실행 권한과 정확한 기능별 기대값은 [검증 정책](stream-verification.md#검증-정책),
[Inventory](project-feature-test-inventory.md), [릴리즈 정책](release-policy.md#출시-전-검증-판정)을 따른다.

기존 실행·계측·회귀를 우선 사용한다. 승인된 구현 검증에 꼭 필요한 최소 계측이나 측정 결함 수정은
목적·범위·비용을 명시하고 기존 실패와 별도로 검증한다. 이를 무조건 금지해 분석만 반복하지 않되,
새 범용 Harness·감독기·Profiler·보고 시스템 개발은 기본 계획에 넣지 않는다.

| 보존할 계약 | 적용·한계 |
| --- | --- |
| R101-C02 v1 | 기존 Native 전체 180초, 준비·혼합 요청·Writer/Generation·Cleanup 및 기존 실패 유지. v2·개발 비교는 대체 PASS가 아님 |
| State45 | [Inventory의 MEDIA-012-STATE-BINDING-F01](project-feature-test-inventory.md)의 관측 2700초/감독 2880초, 양 채널 Recording·자연 삭제 및 삭제 후 관측. 기존 Fixture·Writer 부하·Quota·예약 유지 |
| 공식 Search | Combined p95 ≤ 2000ms, max ≤ 5000ms 및 기존 오류·Timeout·Cancellation 판정 유지. 적용 모집단/계산은 로컬 공식 정의를 따름 |
| Workspace·Resource | Variable과 Copy 각각 **<448MiB**, Combined **<fixed+896MiB**. 448MiB=469,762,048B이며 한도와 같은 값도 실패. 기존 Output·FD·Owner/Admission·Quota를 변경하지 않음 |
| 수명·후속 Gate | Owner RAM 계상·RSS·Anonymous/Scratch Disk·Workspace는 다른 지표. 종료 논리 계상 0을 장시간 누수 없음으로 확대하지 않음. Memory P0·Readiness120·Restart/Recovery·UI·Release는 각 필수 증거와 승인 유지 |

완료는 기존 녹화·검색·증거·A 및 권한/Source 인증/Reader 보호를 유지하고, 승인된 실행 경계와
예약·Stop·예외 반환을 구현하며, 동일 조건의 시스템 비교에서 이득과 trade-off를 확인하고,
누적 제품의 필수 성능·수명·복구·출시 Gate를 각각 충족했을 때다. Native 개선만으로 실제 HTTP,
State45 Timeout/p95 또는 출시가 해결됐다고 선언하지 않는다.

## 범위와 운영 원칙

2채널 State45는 최대 지원 채널 수의 인증이 아니다. 기존 **8채널 개발 profile**, 사용자의
향후 **8~16채널 목표**, 실제 검증된 장시간 운영 용량을 구분한다. 이번 계획에 8/16채널 공식 Gate,
특정 분석 FPS·720p/1080p 처리량·GPU/다중 모델 처리량을 새 필수 완료 조건으로 넣지 않는다.
향후 확장을 막는 무제한 채널별 worker/session·큐나 전역 직렬화 확대는 피한다.

완료된 VA Review/A·서버 자료 안내는 유지한다. v4.6 Correlation, v4.7 QueryPlan API,
v4.8 대화형 UI, v4.9 누적 품질·호환 검증의 기능 배분을 앞당기지 않는다.
후속 버전에는 [실제 채택·검증된 실행 계약](v410-v49-recording-search-roadmap.md#실행과-자원-계약-인계)만
인계한다. 서비스별 기준점 결합과 지원 규모 프로파일도 같은 로드맵의 공통 원칙을 따르며,
이 계획이나 후속 계약 보완을 이미 구현된 기반 또는 현재 v4.5의 추가 구현 범위로 해석하지 않는다.

진척은 승인된 제품 산출물 완성, 실제 실패 조건 감소, 재현 가능한 원인 가설 구분, 공식 Gate
완료로 판단한다. 문서·Commit·테스트 개수나 근거 없는 완성도 백분율로 진척을 주장하지 않는다.
AGENTS의 무진척 반복·범위 확대 중단 기준을 유지한다. 같은 문제의 BLOCKED가 반복되면 유사 후보를
계속 만드는 대신 필요한 계약·범위 결정을 명시한다. 다음 작업은 EP1의 구체적 제품 경계 구현이며
계획을 더 세분화하는 일을 별도 성과로 삼지 않는다.
